# 「探すクエスト」機能 企画メモ

検討日: 2026-09-21
状態: 企画段階。実装は未着手。チームでの採用可否を相談したい。

## 背景・課題意識

- 既存の置き換えダイエットアプリに新機能を追加する形で検討
- 当初「便利さ」路線(AI提案、データ分析での最適化など)を検討したが、既視感が強く不採用に
- 「便利」ではなく「楽しさ」を軸にする方向に転換

## 着目した課題

今のアプリは「レシピを提案すること」までしかやっておらず、**「その材料、実際どこで買うの?」という後工程が完全に手つかず**だった。置き換え食材を実際に入手する段階(どこに売っているか分からない不安・面倒)に着目し、そこを解消しつつゲーム化する。

## 技術的な前提(先に確認済みのこと)

- スーパーの横断的なリアルタイム在庫API(イオン・西友などを横断して在庫が分かるもの)は現状存在しない
- 個別のPOSシステム(Smaregi等)は店舗運営者向けで、外部の一般開発者が使えるものではない
- → 正確な在庫情報は諦め、**ユーザー投稿による集合知**でカバーする設計にした

## コア機能: 「探すクエスト」

1. アプリが今日の置き換え候補を提案(オートミール/豆腐バー/こんにゃく麺など)
2. 近隣スーパーを地図表示(Google Maps API等)
3. ユーザーが探しに行き、見つけたら写真投稿→発見報告としてポイント獲得
4. 未発見の場合も記録し、次回の提案に反映

## クエストのバリエーション

- **選択式クエスト**: 候補のうち1つ見つければOK(ハードルを下げる)
- **レア食材クエスト**: 発見報告が少ない食材は高ポイント
- **エリア制覇クエスト**: 誰も報告していない店舗で発見→「開拓者」バッジ
- **連続クエスト**: 継続日数に応じた達成
- **リベンジクエスト**: 過去に見つからなかった食材の再挑戦

## データ分析の使いどころ

- 店舗×食材の発見率マップ(地域ごとの傾向可視化)
- 個人の「得意/苦手な食材」の分析→成功しやすい提案の優先
- クエストの難易度バランス調整(簡単なものとチャレンジ系を混ぜる)

## 未確定・次に詰めるべき論点

- 既存の置き換えダイエット部分の機能範囲・技術スタックとの整合性
- ポイント・称号のUI/UX設計
- 投稿の信頼性担保(適当な投稿への対策、またはゆるく許容する設計にするか)
- ハッカソンデモ用の仕込みデータ準備(初期投稿ゼロ問題への対処)
- MVP優先順位: ①提案 → ②地図表示 → ③発見投稿、を最初のコアとし、ランキング・キャラ演出は後回し

## 2026-09-21: 地図表示の技術選定について

### 検討した選択肢

| | Google Maps Platform | OpenStreetMap + Leaflet.js |
|---|---|---|
| お店データの充実度 | ◎ 非常に正確・網羅的 | △ 地域差あり、抜けもある |
| 費用 | クレジットカード登録必須(設定すれば実質無料) | 完全無料、カード不要 |
| リスク | 設定ミスで課金の可能性 | リスクほぼゼロ |

- Google Maps Platformは、2025年3月に月$200の共通無料クレジットが廃止され、
  機能(SKU)ごとの個別無料枠(Maps JavaScript APIは月1万回まで無料)に変わった。
  無料枠内でもAPIキー発行には支払い方法の登録が必須
- 「絶対に課金されないようにしたい」場合は、**予算アラートだけでは不十分**
  (通知が来るだけで利用は止まらない)。**API側の「使用量上限(クォータ)」を
  無料枠以下に設定すれば、上限到達時にAPIが物理的に応答を止めるため、
  確実に無課金にできる**(参考: [Google Cloud公式ドキュメント](https://docs.cloud.google.com/apis/docs/capping-api-usage))
- お店データの正確さを優先し、クォータ設定とセットでGoogle Maps Platformを
  採用する方向で検討中

### 追記: 実際にカード登録を試みたところ問題が発生、最終的に解決

標準のAPIキー発行を実際に試したところ、支払い方法の設定でエラーが発生し、
別のカードでは「1回限り¥5,000の前払いが必要」と要求された。前払いは
Google公式ドキュメント上は返金可能な正規の仕組みと確認できたが、実際に
お金が動く点で「絶対に課金しない」という当初の条件とは厳密には合わない
ため、この経路は採用しなかった。

代わりに、**2026年にGoogleが新しく導入した「Maps Demo Key」**を採用した。

- クレジットカード登録が一切不要(公式: [mapsplatform.google.com/maps-demo-key](https://mapsplatform.google.com/maps-demo-key/))
- Googleアカウントのみで即座に取得可能
- 1日あたりの利用上限があらかじめ組み込まれており、自分でクォータを
  設定する必要すらない
- 「プロトタイプ・評価用」と明記されており、ハッカソンの用途に合致
- 検証手段としてYahoo! JAPAN地図API(YOLP、カード不要・1日5万回無料)も
  候補に上がったが、Google純正のDemo Keyで要件を満たせたため見送った
- 注意点: 本番投入する場合は、標準キー(カード登録必須)への切り替えが
  必要になる。ハッカソンのデモ用途を超える場合は要検討

`GOOGLE_MAPS_API_KEY`として`.env`に設定済み。

### 追記(2026-09-21): Maps Demo KeyはPlaces APIにも対応していた

当初「Demo KeyはMaps JavaScript APIのみ対応」と考えていたが、公式ドキュメント
(developers.google.com/maps/demo-key)で確認したところ、**Nearby Search・
Text Search(Places API)にも対応しており、カード登録不要**であることが分かった。
これにより、近くのスーパーを検索する機能(下記)もOverpass API等の別サービスを
使わず、同じDemo Keyのまま実装できた。

## 2026-09-21: AIエージェントによる「クエストのヒント」機能

### きっかけ

「AIエージェントが自動的に食材を探してきてくれたら」という案が出たが、
これは企画の根本方針(「便利さ」ではなく「楽しさ」を軸にする)と矛盾する。
AIが代行してしまうと、実際に足を運んで発見・報告するというクエストの
ゲーム性そのものが失われる。

### 採用した折衷案: 「代行」ではなく「ヒント出し」

AIエージェント(Function Calling)に、**「どの店が見つけやすそうか」を
調べて教えるところまで**を任せ、実際に探す・見つける・報告する行為は
ユーザーに残す設計。

```python
tools = [
    "check_past_discoveries(食材名)",   # アプリ内の過去の発見報告を調べる(信頼できる本物のデータ)
    "get_nearby_stores(現在地)",       # 近くの候補店を取得する
    "search_web(店舗名)",              # 補助的な参考情報のみ(下記の限界を参照)
]
# 目的: 「見つけやすそうな店をヒントとして提示して」(代行はしない)
```

**訂正(`search_web`の限界について)**: 当初「ネットで在庫がありそうか調べる」ツールとして
設計したが、これはこの企画そのものの前提(「スーパー横断のリアルタイム在庫データは
そもそも存在しない」)と矛盾していた。ネット検索で分かるのは、せいぜい「その店が
健康食品コーナーを扱っているか」「チラシに載っているか」程度の**弱い参考情報**に
とどまり、「在庫があるかどうか」を確実に調べることはできない。**信頼できるヒントの
出どころは、実質`check_past_discoveries`(アプリ自身に溜まった、実際の発見報告)
だけ**であり、`search_web`は気休め程度の補助としてのみ位置づける。

### メリット

- クエストのゲーム性(実際に足を運ぶ楽しさ)を壊さない
- ただし「初期投稿ゼロ問題」(コールドスタート)への対策としては、上記の訂正により
  `search_web`があまり頼りにならないと分かったため、**当初期待したほどの効果は
  無いかもしれない**。この点は未解決のまま残る

## 2026-09-21: 画面遷移・ナビゲーションについて

既存の`nav.js`にはすでに8個のタブ(ホーム/レシピ/食事/体重/目標/ラジオ/みんな/設定)が
あり、これ以上増やすとタブバーが窮屈になる。「探すクエスト」専用の9個目のタブは
**追加しない**方針にした。

代わりに、`/recipe`または`/record`で置き換え提案を見た直後に、**「この食材を探しに
行く」ボタンを1つ設置し、そこから遷移する**形にする。ユーザーの行動の流れ
(提案を見る→探しに行く)としても自然で、常時表示されるタブではなく、必要な
ときだけ出てくる画面という位置づけになる。

## 2026-09-21: ピンが増えた時の見やすさ対策

投稿(発見報告)が増えていくと、地図上のピンが密集して見づらくなる懸念が出た。
2つの対策を組み合わせる方針にした。

1. **マーカークラスタリング**: 近くのピンを数字だけの丸にまとめる、定番の
   仕組み。Google Mapsには公式ライブラリ(`@googlemaps/markerclusterer`)が
   あり、自作は不要
2. **表示するピンを、今クエスト中の食材だけに絞る**: 全食材のピンを常に
   表示するのではなく、「今日の候補: オートミール」のような、進行中の
   クエスト対象の食材のピンだけを表示する。見やすさだけでなく、
   **無関係なピンに惑わされず探しやすくなる**という利点もある

## 2026-09-21: 発見報告へのコメント欄・プライバシー対応

実際に画面を作って動かしてみたところ、2点の改善点が見つかった。

- **コメント欄の追加**: 写真だけでなく「入口すぐの棚にあった」のような一言メモを
  添えられると、他のユーザーが探すときの助けになる。`discoveries`テーブルに
  `comment`(任意)列を追加し、報告フォーム・地図のInfoWindow表示の両方に反映した
- **`user_id`の非公開化**: 地図はみんなで共有される設計のため、発見報告の
  一覧APIが返すデータに`user_id`が含まれていると、他ユーザーに個人を特定
  しうる識別子が渡ってしまう。レーティング機能で確立した「他ユーザーの
  情報を無断で見せない」という方針([README参照](../suggestion_diversity/README.md))
  に沿い、`GET /discoveries`のレスポンスからは`user_id`を除外した

## 2026-09-21: 「開拓者」バッジ(エリア制覇クエスト)を実装

クエストのバリエーション案のうち、まず**エリア制覇クエスト**(誰も報告していない
店舗で発見→「開拓者」バッジ)を実装した。他の案(レア食材クエストのポイント制、
連続クエスト、リベンジクエスト)はポイント制度や「未発見」記録など前提となる
仕組みが追加で必要になるため、より単純な本機能から着手した。

- `discoveries`テーブルに`is_pioneer`(bool, default false)列を追加
- `POST /discoveries`で、保存前に`is_new_store(store_name)`でその店舗の
  既存報告の有無をチェックし、無ければ`is_pioneer=true`で保存
- 同じ報告(1回の投稿で複数食材を選んだ場合)は、写真アップロードと同様に
  店舗の新規判定も1回だけ行い、保存する全行に同じ`is_pioneer`値を使う
  (同じ来店で複数食材を見つけても、判定がブレないようにするため)
- 地図のInfoWindowと、報告成功時のメッセージにバッジ表示を追加
- ポイント制は「もっと簡単なものがいい」という判断で見送り、バッジ表示のみとした

## 2026-09-21: 近くのスーパーを地図・プルダウンに表示

これまでは自分の発見報告の位置(現在地クリック・ドラッグ)しか指定できなかったが、
「近くに実在するスーパーの位置をあらかじめ表示してほしい」という要望を受け、
Places API(Nearby Search、`type: "supermarket"`、半径2km)で周辺のスーパーを
検索し、以下2箇所に反映した。

- 地図上にグレーの丸ピンで表示(現在地=青丸、報告ピン=赤ピン、発見報告済み=
  通常の赤マーカー、と色で役割を区別)
- 「近くのお店から選ぶ」プルダウンにも一覧表示。選ぶ(またはグレーのピンを
  クリックする)と、報告ピンが自動でその位置に移動し、お店の名前欄も自動入力される

地図クリック・ドラッグでの手動指定も引き続き残しており、「近くのお店から選ぶ」
「自分でピンを置く」の両方に対応した形になっている。

## 2026-09-21: 店名の表記ゆれ対策(文字列正規化→位置判定に変更)

「開拓者」バッジの判定は当初、店名の文字列一致(正規化して比較)で行っていた。
しかし、Unicode上の表記ゆれ(全角/半角、大文字/小文字、空白の有無)は吸収できても、
「イオン」と「AEON」のような表記そのものの違いや、「イオン渋谷店」と
「イオン渋谷駅前店」のような省略・詳しさの違いには対応できず、不完全だった。

判定基準を店名の文字列一致ではなく、**位置(緯度経度)の近さ**に変更した。
半径`PIONEER_RADIUS_METERS`(50m)以内に既存の発見報告が無ければ「開拓者」と
みなす。店名の書き方に関係なく判定でき、追加のAPIも不要(既存の`lat`/`lng`
だけで完結する)。`is_new_store(lat, lng)`は全発見報告とのhaversine距離を
計算して判定する簡易な実装で、Places APIのような有料APIは使わない。

## 検討時点での所感(参考)

- 機能6(食事写真からのカロリー計算)は画像認識の難易度を理由に見送られているが、
  この機能で使う写真投稿は「画像認識」ではなく「発見報告の証拠」としての利用のため、
  技術的なハードルは機能6とは別物(単純な画像保存・表示で済む)
- コールドスタート問題(初期投稿ゼロ)は、今日何度もぶつかった壁と同種の課題。
  仕込みデータでの対処が必要
- 規模としては、今日実装した「提案の多様性チェック」機能と同等かそれ以上。
  3週間のハッカソンの残り時間との兼ね合いを、チームで相談する必要がある
